Part one of three · 50 minutes

Is it actually good, and is it actually safe?

Why component metrics lie, what bias and PII actually cost, and what breaks only after it ships.

Component metrics versus the whole system

Five stages at 95% each is not a 95% system

  1. 01Extract95%
  2. 02Retrieve95%
  3. 03Memory95%
  4. 04Tool call95%
  5. 05Generate95%

0.955 ≈ 77%, for one turn needing all five stages to succeed together. A real conversation needing this to hold across six turns in a row: 0.9530 ≈ 21%. No single component metric on this system would ever show a number below 95%, yet the system a user actually experiences is right there at 21%.

The metric that measures the real thing

Run the same task , not once

tau-bench scores a run by comparing the database state at the end of the conversation against an annotated goal state, a deterministic, faithful check, not an LLM guessing whether it went well.

Trap

"It passed the eval" almost always means pass1. A team that never re-runs its own scripted scenarios has never actually measured whether their agent is reliable, only whether it can succeed once.

# pass^1: succeeds at least once
pass_1 < 50%

# pass^8: succeeds all 8 times in a row
pass_8 < 25%

Real numbers, tau-bench (arXiv:2406.12045), not illustrative round ones.

The harder, more realistic test

What happens once the user can act too

Agent (has tools)
User (has tools too)
The split that matters operationally

tau2-bench (arXiv:2506.07982) separates reasoning failures (the agent chose the wrong thing) from coordination failures (the agent could not successfully guide the user's half). Performance drops significantly the moment the user can act too, and the two failure types need different fixes: a better model for one, clearer instructions to the user for the other.

Check question

An agent scores 90% pass1 but only 30% pass8 on the same task. What does that gap actually mean?

The idea behind the question

A single pass/fail number can never distinguish "capable" from "reliable." Only repetition can.

Not just tone, task performance itself

One variable changed, and the score moves anyway

The technique, in one line

Run the identical task twice: once with no identity cue, once with a demographic persona cue added that has nothing to do with what is actually being asked. Model, tools, and policy stay the same in both runs. Any score difference is bias, not noise.

Why this is not a tone question

Persona-conditioned bias in chatbot text is already well documented. A 2026 workshop paper (Cao, Sun & Yue, arXiv:2602.12285) found the same conditioning moves agent task success itself, by up to 26.2% across widely deployed models. A system that only ever tests one persona has never measured whether this exists in its own agent.

The mechanism behind every real PII pipeline

No single technique catches everything, so layer four

  1. 01Regex / deny-listEmails, phone formats
  2. 02ChecksumA Luhn-valid card number, not just digit-shaped
  3. 03Entity recognitionA name or address in free text
  4. 04Context"SSN:" before nine digits is a stronger signal than the digits alone
Then one of five operators

Redact (delete), mask (***-**-1234), hash (one-way, still linkable), replace (a synthetic stand-in), or encrypt (reversible, for an authorised lookup). This is Presidio's own layered architecture, the field's most widely deployed open building block for this.

Redacting "user's email is X" to "user's email is [REDACTED]" also destroys the agent's own ability to answer "what's the email you have on file for me," a legitimate request, not an attack. What a memory system chooses to store (Module 4) is exactly what a PII pipeline downstream has to account for.

Why not just one big regex denylist

A denylist alone never catches a name or a home address stated in free text, and it never catches a digit string that merely looks like a card number, hence entity recognition and checksum validation as separate layers. Each layer alone is cheap to build and each alone still misses whole categories, the layering is the actual mechanism, not any single technique.

Not textbook, live law

One deadline already passed, one deferred

  1. Aug 2026EU AI Act Article 50Live law. A chatbot must disclose it is an AI.
  2. TodaySept 2026Article 50 already binds any EU-reachable deployment.
  3. Dec 2027High-risk (Annex III)Deferred by the EU's Nov 2025 Digital Omnibus, not cancelled.
Stated precisely, not vaguely

Penalties for breaching Article 50's transparency duty run up to EUR 15 million or 3% of global turnover. A team's own agent is very unlikely to be classified high-risk, but if it is reachable by any EU user, the disclosure duty is already live law today, not a future compliance date to plan around later.

A line in the first turn, "You're chatting with an automated assistant," satisfies the duty. Burying it in a terms-of-service page nobody reads does not: the obligation is that the user actually knows, in plain terms, at the point of use.

What never shows up in an offline eval at all

Three costs a demo never has to pay

ConcernWhat it actually means
Latency budgetA p50 average hides the p95/p99 tail that ruins one user in twenty; a budget is stated per percentile, across every hop, not just the model call.
Cost per conversationNot cost per call: one conversation's memory search, retrieval, rerank, and judge calls all bill against the same user-visible reply.
DriftA provider updates the model behind a pinned version string, or the same prompt behaves differently next month, with nothing in the code changed.
This is not abstract

This course's own demos pin an explicit model version string in every module instead of "latest," for exactly this reason. Drift is not a new idea today, it is the first time the discipline students have followed since Module 1 gets named and explained.

A support agent's first-token latency budget stated as "p95 under 3 seconds, p99 under 6," not "usually fast." A team that has never measured its own p95 has no budget at all, only a vibe.

Part two of three · 40 minutes

What the papers actually found

tau-bench and tau2-bench in full depth, then the paper that measures the LLM-as-judge blind spot directly.

Yao, Shinn, Razavi & Narasimhan, 2024 · arXiv:2406.12045 · named in the syllabus

A user simulator, a policy, and a ground truth you can check

  • Two domains: retail and airline customer support, each with real API tools and written policy guidelines the agent must follow, not just a task to complete.
  • A language model plays the user, so the conversation is dynamic, not scripted turn by turn in advance.
  • Scoring compares the database state at the end of the conversation against an annotated goal state: deterministic, not an LLM guessing.
Why database-diff, not an LLM judge

A clean, checkable ground truth is exactly what makes tau-bench's own scoring trustworthy without a judge at all. It costs nothing extra to run once the goal state is annotated. The tradeoff: most real deployments have no clean database state to diff against, which is precisely why an LLM judge gets reached for instead, and precisely why its blind spots (two slides ahead) matter.

# run the same task k times, independently
outcomes = [run_task(task) for _ in range(k)]

# succeed only if EVERY run succeeded
pass_k = all(outcomes)

Real result: gpt-4o-class agents, retail domain, pass1 < 50%, pass8 < 25%.

Read critically

Two domains, both customer support. The user simulator is itself an LLM, which can behave unrealistically in ways a real customer would not. Treat pass^k as a lower bound on the gap between "looks capable" and "is reliable," not a universal constant that transfers unchanged to every domain.

Barres, Dong, Ray, Si & Narasimhan, 2025 · arXiv:2506.07982 · named in the syllabus

Dual control: a telecom domain where both sides hold tools

  • Modelled formally as a Dec-POMDP: agent and user both act on one shared, dynamic environment, neither with full visibility into the other's state.
  • A compositional task generator builds diverse, verifiable tasks from atomic components, so task difficulty is controlled, not accidental.
  • Fine-grained ablations separate reasoning errors (wrong decision) from communication/coordination errors (failed to guide the user correctly).
The headline result

Performance drops significantly the moment the environment moves from single-control (agent only) to dual-control (agent and user both acting). The paper's own framing: an agent has to reason well and guide the user's actions, and today's agents are noticeably worse at the second half.

Why this benchmark exists at all

tau-bench keeps the user passive on purpose, to isolate agent reasoning cleanly. That cleanliness is also its limit: a real support call is not passive, the customer restarts their own router mid-call. tau2-bench is not a harder version of the same test, it is testing a capability tau-bench cannot see at all.

Mohammadi, 2026 · arXiv:2609.00038 · single-author preprint, under review

The evidence for the syllabus's own claim: how much a judge under-detects

Not a third anchor paper, this is the concrete source for the exact number the syllabus asks about. A deterministic support-desk environment with a fault injector that breaks exactly one known step, each fault labelled loud (visibly broke) or silent (still looked fine), scored across 400 trajectories.

Outcome-only judge (today's default) 84% of loud faults caught. Only 45% of silent faults caught. 33% of fully correct trajectories flagged as faulty.
Step-rubric (trajectory-level) judge 77% silent-fault recall, zero false alarms. Costs 3x the outcome-only judge.
The same critical read this course has asked for every module

A number is not weaker for being new, but say what it is

trajectory-judge (arXiv:2609.00038)Zheng et al., 2023 (arXiv:2306.05685)
StatusSingle-author preprint, under review at a workshopNeurIPS 2023 Datasets and Benchmarks, peer-reviewed
What it measuresSilent versus loud fault detection, ground truth by constructionPosition, verbosity, and self-enhancement bias in LLM judges
What it does not claimThat judges are uselessThat judges are unbiased
Put together

Zheng et al. also found strong judges reach over 80% agreement with human preferences, the same level humans reach with each other. Judges are not useless, they have specific, now-measured blind spots, and the newest measurement is about exactly the failure mode (silent, trajectory-level) an outcome-only default cannot see.

Paired discussion · 9 minutes

Name an actual step, not a general worry

With the person next to you: where would an outcome-only LLM-as-judge most likely miss a real failure in your own team's agent? A specific tool call whose result is silently wrong but whose downstream reply still reads fine, not "it might miss things" in general.

  • Which tool call in your pipeline, if it silently returned the wrong value, would the final reply still look correct?
  • Would your own current eval (if you have run one) have caught that, honestly?
  • Is this closer to a tau-bench-style failure (the agent alone got it wrong) or a tau2-bench-style one (the handoff to the user broke down)?
This is the syllabus's own framing question

Today's lab builds a step-rubric judge specifically because an outcome-only one would miss over half of exactly this kind of failure, per the numbers two slides ago.

Capture everything, not just the final reply

A fixed set of conversations, every step recorded

SCENARIOS = [
  {"turns": [...], "expected_outcome": "order status: shipped"},
  # 5-10 scenarios covering your team's actual domain
]
trajectory = {
  "turns": [...],
  "tool_calls": [{"name": ..., "args": ..., "result": ...}],
  "final_reply": ...
}
for scenario in SCENARIOS:
    trajectory = run_and_capture(agent, scenario)
    save(trajectory)
Grade the steps, then repeat to test reliability

A structured-output judge, then run it k times

schema = {"type": "object", "properties": {
  "step_verdicts": {"type": "array"},
  "silent_fault_suspected": {"type": "boolean"},
  "overall_pass": {"type": "boolean"}
}}
verdict = judge(trajectory, schema=schema)
# verdict.overall_pass, verdict.silent_fault_suspected
results = [run_and_grade(scenario) for _ in range(5)]
pass_k = all(r.overall_pass for r in results)
Decide out loud, with your partner, before you code

A two-person team says the step-rubric judge is not worth 3x the cost for their small project. What is the strongest response?

Run it twice, swap only the persona cue

baseline = "I need to check my order status."
persona  = "I'm a [demographic cue]. I need to check my order status."
score_baseline = run_and_grade(baseline)
score_persona  = run_and_grade(persona)
delta = score_baseline - score_persona
# report this number, honestly, even if it is uncomfortable

So you recognize them instead of debugging blind

Four bugs that show up in almost every team's harness today

SymptomUsual cause
pass^k always equals pass^1The harness is not actually re-running the scenario independently, it is replaying a cached result
The judge always says passOnly the final reply was ever fed to the judge, tool calls were never captured
The bias probe shows no delta, everThe persona variant changed more than one variable, or was never actually run, only described
The PII probe passes triviallyIt checks the memory store's own internals instead of what the agent actually says out loud
Open work · rest of the block

Regression set, judge, bias probe, PII probe, one scorecard

  1. Finish the scripted regression set and trajectory capture against your own agent.
  2. Wire in the step-rubric judge and run a real pass^k, not just pass^1.
  3. Run the bias probe and the PII-leakage probe, both required, neither optional.
  4. Assemble one scorecard file. Open the PR, Closes #5 in the description links it automatically.
A written claim is not the deliverable

Issue 5 needs a real pass^k number from a real repeated run, a real bias-probe delta, and a real PII-leakage assertion that actually fails when it should. If a live connection drops, keep building against saved trajectories, none of today's scoring needs a live call once a trajectory is already captured.
