Part one of three · about 40 minutes

Is it good, and is it safe?

Why component scores lie, how to repeat a test, and how to check bias, personal data and cost.

Component metrics versus the whole system

Five parts at 95% are not a 95% system

Definition

Component metric: a score for one part, such as extraction accuracy. End-to-end metric: a score for the whole conversation. The multiplication above assumes the stages fail independently, which real systems only roughly do.

Success once is not success every time

One run says little. Repeat it.

Tries (k)Any try succeeds (pass@k)All tries succeed (pass^k)
175%75%
2100%50%
3100%25%
4100%0%
Invented for teaching: one task, 4 trials, 3 succeeded (c = 3 of n = 4).
Definition

Trial: one full run of a task. pass@k: at least one of k trials succeeds. pass^k: all k trials succeed. For pass^2: of the 6 ways to choose 2 trials from 4, 3 are two successes, so 3 / 6 = 50% (formula C(c, k) / C(n, k)).

Check question

An agent scores 90% on pass^1 but only 30% on pass^8 for the same tasks. What does the gap mean?

Not only tone: results themselves can change

Same task, one extra detail, compare the scores

Definition

Bias probe: a test that holds a task fixed and changes only an identity cue. Identity cue: a detail about a person, such as age, gender, religion or job, that should not change the answer.

Careful: two different designs

In the paper the persona is given to the agent: "From now on, you are a [role]". In our demo the cue is in the customer's message. Same logic, different place.

What an offline test never shows

Average speed hides the slow replies

PercentileMeaningExample (invented)
p50The median: half of replies are faster1.0 second
p9595 of 100 replies are faster3.0 seconds
p9999 of 100 replies are faster6.0 seconds
Percentile: p95 = 3.0 s means 5 replies in 100 take longer than 3 seconds, and 1 reply in 100 takes longer than 6 s (p99). p50 is the median, not an average.
Definition

Latency budget: the time you allow for a reply, stated per percentile and counted over every step: memory search, retrieval, reranking, the model, the checks. "p95 under 3 seconds, p99 under 6" is a budget. "Usually fast" is not.

Two more things a demo never pays for

Two hidden risks: total cost, and model drift

Cost per conversation

Add up every call

Count every call in the conversation, not one call.

Invented for teaching: 8 turns × 6,000 tokens = 48,000 tokens. At a made-up price of USD 0.50 per million tokens, that is USD 0.024 for one conversation.

Drift

Nothing changed, but results did

The model behind a name can change, or behave differently next month, with no change in your code.

So pin an exact model version and re-run a fixed set of test questions on a schedule.

Why not cost per call

A conversation bills for memory search, retrieval, reranking, the answer and every judge call. A cost per call hides most of it.

A benchmark where the agent must talk to a user and follow rules

What it is
A research paper that also releases a benchmark (a standard test) and code. It comes from Sierra, a company. It is a preprint: its first page says "Under review".
Title
"tau-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains"
Authors
Shunyu Yao, Noah Shinn, Pedram Razavi and Karthik Narasimhan, Sierra.
When

Read it

The problem it addresses

Older agent tests give the agent all the information at once and ignore written rules. A real customer talks step by step, and the agent must follow the company's rules.

Figure 1 of the paper

Tools, a rulebook, and a user with a goal

How to read it

Left: tools to read and write a database, a rulebook, and a simulated user with a secret goal. Right: the rule blocks the change, so the agent finds a legal way to help: cancel and rebook.

Method

Compare the database at the end with the goal

Definition

Reward: 1 if the final database equals the goal database, else 0. The paper has two domains: retail (115 tasks) and airline (50 tasks). Temperature = how random the model is: the agent runs at 0 (steady), the simulated user at 1 (varied), so conversations vary. Example: final order status = cancelled matches the goal, so reward 1.

Then repeat it

For the best model, gpt-4o, success in one try is about 61% on retail. But when the same task must succeed in all 8 tries, it falls below 25%.

Analysis

Mostly wrong details and missed rules

Figure 5 and text of the paper. They sampled 115 retail runs; 40 failed, 4 of those were typos in the task, 36 were agent errors.
What the failures look like

Example from the paper: the policy says an exchange tool may be called only once. The agent exchanged one item first, so the second item was never exchanged. Removing the policy text from gpt-4o's prompt cut airline success from 33.2 to 10.8.

Author

When

Read it
Local copy (PDF) · arXiv page · code

The question it asks

Can an LLM judge find a mistake that is hidden behind a correct-looking reply?

Figure 1 of the paper

Same reply, different truth

How to read it

Both runs end with the same reply. In the bottom run a required check (eligibility) was skipped. The outcome judge flags both runs: it cannot tell them apart (difference score 0). The step judge passes the clean run and flags only the faulty one (difference score 1).

Method

Build faults on purpose, so the answer is known

Definition

Paired discrimination (difference score): how often the judge flags a faulty run, minus how often it flags the clean run it came from. If a judge flags everything, the share of faults it finds is high but the difference score is zero.

Results

Looking only at the reply fools the judge

Judge (14B model)Finds loud faults (high is good)Finds silent faults (high is good)False alarms on clean runs (low is good)Time per run
Outcome-only: request and reply84.0%45.1%33.0%3.5 s
Step by step: every step98.4%76.6%0 of 10010.4 s
Table 3 and Table 9 of the paper. 100 clean, 175 silent and 125 loud runs. The step judge's 0 false alarms has a 95% interval up to 3.6%.
Raw recall can mislead

The outcome-only judge "catches" 45% of silent faults, but it also flags 33% of clean runs. After subtracting that, its real detection of silent faults is +0.048, almost nothing (the paper pairs each fault with its own clean run). The step judge costs about three times as much per run.

Limits

What this paper cannot tell you

What the paper reportsA question to ask
One 14-billion-parameter local model, one promptA larger or differently prompted judge may behave differently. The paper says its findings are scoped to this testbed.
A made-up support desk with six fault typesReal agent failures are less tidy.
0 false alarms in 100 clean runs100 runs are too few to trust it in production: the true false-alarm rate could still be up to 3.6%.
A smaller 8B judge flags 397 of 400 runsSome models cannot be used as judges at all with this prompt.
The step judge did not check whether the reply's promises were trueIt caught one invented promise every time, but the other three only once in 42 tries.
The classic paper on LLM-as-a-judge

Useful judges with known blind spots

Zheng et al. (2023)Finding
Agreement with humansA strong judge (GPT-4) agrees with human preferences over 80% of the time, as often as two humans agree with each other.
Position biasMany judges favour the answer shown first. Only GPT-4 stayed consistent in more than 60% of swaps.
Verbosity biasJudges prefer a longer answer, even when the extra words add nothing.

Part three of three · about 40 minutes

Watch it built

I run the evaluation harness part by part and explain every line. You watch and follow. Nobody codes in class.

What I run, in order

One script, six steps, four checks

  1. A toy agent that looks up an order, and sometimes gets a stale answer on purpose.
  2. Capture the whole run, not just the reply.
  3. A step judge that reads the run against the known-correct outcome.
  4. Repeat each scenario three times: pass^1 and pass^3.
  5. A bias probe and a personal-data probe.
  6. One scorecard.
File

demos/module-05/eval_harness.py

Remember

The toy agent is not your project agent. The four checks are what your team wires to its own agent.

Demo step 1

Make a silent fault on purpose

ORDERS = {"A100": {"status": "shipped",
                     "carrier": "Aramex",
                     "eta": "2 business days"}, ...}
FLAKE_RATE = 0.4

def get_order_status(order_id, attempt_seed):
    rng = random.Random(f"{order_id}:{attempt_seed}")
    if rng.random() < FLAKE_RATE:
        return {"status": "processing",   # stale, wrong
                "carrier": None,
                "eta": "pending"}
    return ORDERS[order_id]
What to notice
  • The tool is right most of the time
  • 40% of calls return a stale answer
  • A stale answer looks normal: no error, nothing broken
  • The seed makes the pattern repeatable

A silent fault: the reply built from it will sound fluent and be wrong.

Demo step 2

Save the steps, not only the answer

def run_agent_turn(order_id, attempt_seed,
                   persona_prefix=""):
    user_line = persona_prefix + (
      f"Can you tell me the status of my order {order_id}?")
    tool_result = get_order_status(order_id, attempt_seed)
    reply = call_model(user_line, tool_result)
    return {"user_turn": user_line,
            "tool_calls": [{"name": "get_order_status",
                            "args": {"order_id": order_id},
                            "result": tool_result}],
            "final_reply": reply}
What to notice
  • The record keeps the tool call and its result, not only the reply
  • The model is told to state the status plainly and never to mention a stale lookup
  • So a wrong tool result becomes a confident wrong reply
Why capture it

This record is the trajectory. A judge can only check what it is shown.

Demo step 3

Grade the steps against a known answer

JUDGE_SCHEMA = {"step_verdicts": [...],
                "silent_fault_suspected": bool,
                "overall_pass": bool}

def judge_trajectory(scenario, trajectory):
    prompt = f"""
    Known-correct outcome: {scenario['expected_outcome']}
    Customer turn: {trajectory['user_turn']}
    Tool calls: {tool_listing}
    Agent reply: {trajectory['final_reply']}
    Grade step by step, not just the reply. Does the
    tool result match the known-correct outcome?"""
    return call_model(prompt, schema=JUDGE_SCHEMA)
What to notice
  • It is shown the tool call and its result
  • It is given the known-correct outcome to check against
  • It answers in a schema (Module 1): a checkable object, not free text

Same idea as the paper's step judge: check each step, not only the reply.

Demo step 4

Run it k times and ask: all of them?

def pass_k_for_scenario(scenario, k=3):
    attempts = []
    for i in range(k):
        traj = run_agent_turn(scenario["order_id"],
                 attempt_seed=f"{scenario['scenario_id']}-{i}")
        verdict = judge_trajectory(scenario, traj)
        attempts.append(verdict["overall_pass"])
    return {"pass_1": attempts[0],
            "pass_3": all(attempts)}

So you recognise them instead of debugging blind

Four problems you will meet

SymptomUsual cause
pass^k always equals pass^1The harness replays one saved result instead of running the scenario again
The judge always says passOnly the final reply was given to the judge, tool calls were not captured
The bias probe never shows a differenceMore than one thing changed, or the second run never happened
The personal-data probe passes too easilyIt checks the store's inside, not what the agent can say or find
Fastest check

Open one saved trajectory by hand before you trust any score. If you cannot see the fault yourself, the judge probably cannot either.
