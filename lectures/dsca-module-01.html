Part one of one · 50 minutes

Why this replaces classical NLP

Not a new tool bolted onto the old pipeline. The old pipeline's first two stages, done a different way, with the failure case designed in from the start.

The reference architecture

Every conversational agent does five things. This course builds each one once.

Understand
Turn the raw utterance into and , structured.
Decide
Hold state across turns, ask for what's missing, route to a specialist or a human when needed.
Respond
Ground the answer in a real source, cite it, refuse cleanly when the source does not cover it.
Remember
Recognize a returning user, recall what mattered, forget what should not persist.
Evaluate
Prove, with a real test suite, that the first four stages still work before anyone ships a change.
The one rule that matters this module

Understand is not "run a script and hope." It is a call with a contract: a schema the model's output must satisfy, and a defined answer for when it does not.

Because a pipeline implies each stage always runs, in order, once. A real agent skips stages, revisits them, and sometimes runs two at once. The five names are what to call each job, not a fixed sequence to obey.

What changed, and why it is not a downgrade

One call replaces a trained classifier, a trained tagger, and the team that maintained both

Classical NLU used two separate trained models: an and an , trained separately, that could silently disagree.

  • replaces the classifier: the "function" the model can call is named after the intent.
  • replaces the tagger: the schema's fields are the entities.
  • Adding a new intent is now editing a schema, not collecting labeled data and retraining two models.
# One schema replaces a classifier and a tagger
SCHEMA = {
  "party_size": "integer | null",
  "day":        "string | null",
  "time":       "string | null",
}
# the model returns exactly this shape, or the
# call fails validation and the fallback runs
Trap

"The model can do anything" is not the same claim as "the model's output is validated." This course only trusts the second one.

Diagnostic walkthrough

The hook's own correction, turned into an updated object in four steps

user: "Book me a table for 4 on Monday at 7pm"

state = {
  "party_size": 4,
  "day": "monday",
  "time": "7pm"
}
current state: {"party_size": 4, "day": "monday", "time": "7pm"}
user just said: "actually, make that Tuesday"

# the model is asked to return the updated
# state, keeping any field the user did not change
state = {
  "party_size": 4,        // carried forward
  "day": "tuesday",      // updated
  "time": "7pm"        // carried forward
}
reply: "Sure, updating that for you!"
→ does not match SCHEMA, validation fails
→ fallback runs: retry once, or ask a clarifying
   question, your team decides which
Check question

In the walkthrough, why did party_size survive the correction turn unchanged?

Why this matters before the lab

Every team's extraction call needs to pass the current state in, every turn. Forgetting this is the single most common bug in the next segment.

Both providers enforce the schema at decode time. Neither is "asked nicely" to format correctly, the constraint is structural.

A decision made now, paid for in Module 5

Log the three example utterances today. Module 5 needs exactly them.

Module 5's regression harness is scripted conversations run automatically. The cheapest way to have those scripts is to save the ones you write today, verbatim, with the extraction result they produced.

  • Save your team's 3 required utterances as a fixture file, not just in a notebook cell you might overwrite.
  • Save one malformed or edge-case input too. That becomes a Module 5 regression case for free.
The alternative, and why it is worse

Build it

Pattern, pairing, and the bugs most likely to hit you. The commit happens off-session.

Adapt the pattern from slide 7 to your own domain

Issue 1, in your own repository

  1. Write your team's 3 required utterances: one clean, one missing a needed detail, one that should fail cleanly.
  2. Adapt the schema from the walkthrough to your domain's fields, in agent/understanding.py's extract().
  3. Decide your fallback: retry once, or ask a clarifying question. Either is fine, undecided is not, write it down.
  4. Pair up. One person can start the schema while another drafts the utterances.
Deliverable, finished off-session before Module 2

extract() working against your 3 utterances, the fallback decision written in the pull request, tests updated, Issue 1 merged.

Read this before you hit it, not after

Three bugs account for most of what stops teams here

SymptomUsual cause
A field is always emptyThe schema marks it optional when the utterance always states it, or the reverse
Fields reset every turnCurrent state is not being passed into the next call, see slide 7
The call raises an errorThe provider key was never actually tested, run verify_setup.py again

It is fine to pick one and revisit it. What matters for Issue 1 is that a decision exists and is written down, not that it is the best possible one. Module 5 will test it against real failures, that is when to reconsider.
