Part one of one · 50 minutes

Why this replaces classical NLP

Not a new tool bolted onto the old pipeline. The old pipeline's first two stages, done a different way, with the failure case designed in from the start.

The reference architecture

Every conversational agent does five things. This course builds each one once.

Understand
Turn the raw utterance into and , structured.
Decide
Hold state across turns, ask for what's missing, route to a specialist or a human when needed.
Respond
Ground the answer in a real source, cite it, refuse cleanly when the source does not cover it.
Remember
Recognize a returning user, recall what mattered, forget what should not persist.
Evaluate
Prove, with a real test suite, that the first four stages still work before anyone ships a change.
The one rule that matters this module

Understand is not "run a script and hope." It is a call with a contract: a schema the model's output must satisfy, and a defined answer for when it does not.

A pipeline implies each stage runs in order, once. A real agent skips and revisits stages. The five names describe a job, not a fixed sequence.

What changed, and why it is not a downgrade

One call replaces a trained classifier and a trained tagger

Classical NLU used two separate trained models: an and an , trained separately, that could silently disagree.

  • replaces the classifier.
  • replaces the tagger.
What this buys you

Adding a new intent is now editing a schema, not collecting labeled data and retraining two models.

The cost this actually removes

A production intent classifier typically needed dozens to hundreds of labeled utterances per intent before it was reliable, and every new intent meant repeating that collection-and-retraining cycle for both models. A schema and its field descriptions replace that entire data-collection step; the cost that remains is prompt and schema design, not labeling.

The metric that changes underneath this too

Classical NLU is graded per component: intent accuracy and slot F1, so one wrong slot in an otherwise-correct parse still counts as mostly right. A schema-validated extraction call is graded on the whole object at once, exact match on every field: one wrong field fails the entire turn. This is a stricter bar, not a softer one, and it is the reason validation and a defined fallback (next slides) are not optional extras.

Trap

"The model can do anything" is not the same claim as "the model's output is validated." This course only trusts the second one.

Not a request, a constraint

The schema is compiled into the decoding process itself

"Structured output" is not the model being asked nicely to format its reply as JSON. The schema you pass in is compiled into a grammar, and that grammar constrains which tokens the model is even allowed to produce at each step of generation.

after {"party_size": 4, "day": "tue, the only legal
next tokens are ones that keep the output on a path
matching SCHEMA. A token that would produce invalid
JSON, or a field the schema does not define, gets
zero probability. It is never sampled, not just
discouraged.
What this guarantees, and what it does not

The output will parse as valid JSON matching your schema's shape, every time. It says nothing about whether a value inside that shape is correct. "party_size": 4 can be perfectly valid and still be a hallucinated guess.

You can, and it often works. But "often" is the problem: a model asked nicely can still reply with a trailing sentence, a markdown code fence, or a field it invented. Grammar-constrained decoding removes that failure mode structurally, not by getting better at prompting.

Diagnostic walkthrough

The hook's own correction, turned into an updated object in four steps

user: "Book me a table for 4 on Monday at 7pm"

state = {
  "party_size": 4,
  "day": "monday",
  "time": "7pm"
}
current state: {"party_size": 4, "day": "monday", "time": "7pm"}
user just said: "actually, make that Tuesday"

# the model is asked to return the updated
# state, keeping any field the user did not change
state = {
  "party_size": 4,        // carried forward
  "day": "tuesday",      // updated
  "time": "7pm"        // carried forward
}
reply: "Sure, updating that for you!"
→ does not match SCHEMA, validation fails
→ fallback runs: retry once, or ask a clarifying
   question, your team decides which

Gemini enforces the schema at decode time. It is not "asked nicely" to format correctly, the constraint is structural.

Why Gemini, and not OpenAI or Anthropic

This is a course choice, not a technical superiority claim: OpenAI's function calling and Anthropic's tool use enforce structured output the same structural way, at decode time, not by asking nicely either. Gemini's free tier is the most generous of the three for a classroom running the same demos across thirty machines with no card on file, that is the actual reason, say so plainly if asked. Everything this module teaches about the schema-as-contract carries over unchanged to either alternative.

Same method, your own domain

Four blanks to fill, not a new architecture

  1. Name the fields your domain needs, the way party_size named one for booking.
  2. Write the one-line description the model sees for each field.
  3. Decide what counts as valid for each field.
  4. Decide the fallback: what happens when a field cannot be filled.
What does not change

The call, the validation, and the fallback wiring from this morning's lecture are already correct. Only the field names and descriptions are yours to write.

Three utterances, chosen to fail in different ways

A good test set breaks your own fallback on purpose

UtteranceWhat it tests
States every field cleanlyThe happy path works at all
Leaves one required field outValidation actually catches the gap
Is ambiguous or contradicts itselfThe fallback you chose actually runs
Trap

Three clean utterances is not a test set, it is one utterance said three ways. If none of your three can fail, you have not written your fallback yet, you have just not needed it.

Adapt the pattern you just saw to your own domain

Issue 1, in your own repository

  1. Write your team's 3 required utterances: one clean, one missing a needed detail, one that should fail cleanly.
  2. Adapt the schema from the walkthrough to your domain's fields, in agent/understanding.py's extract().
  3. Decide your fallback: retry once, or ask a clarifying question. Either is fine, undecided is not, write it down.
  4. Pair up. One person can start the schema while another drafts the utterances.

When extraction fails or is incomplete

Three honest options, not one correct answer

StrategyWhat it costsWhat it protects
Ask a clarifying follow-upOne more turnNever acts on a guess
Apply a safe defaultRisks a wrong assumptionKeeps the conversation moving
Escalate or refuse cleanlyWorst experience of the threeNever silently fails
There is no house style yet

This course does not mandate one strategy. Your team picks based on what your domain can tolerate getting wrong, and writes that reasoning down. Module 5 is where you find out if the choice held up.

Decide out loud, with your partner, before you code

A ticket's urgency field cannot be determined from the utterance. Which strategy fits best for a domain where acting on a wrong urgency wastes a technician's morning?

Issue 1's third acceptance criterion, satisfied in two sentences

Write the reasoning down, not just the code

# Fallback behavior
#
# When urgency cannot be determined, we ask one
# clarifying question rather than defaulting, because
# a wrong default here costs a technician's morning.
This is graded

"The fallback behavior is documented in the pull request" is a checklist item on Issue 1, not a suggestion. A decision that only lives in someone's head does not satisfy it.

Three bugs account for most of what stops teams here

SymptomUsual cause
A field is always emptyThe schema marks it optional when the utterance always states it, or the reverse
Fields reset every turnCurrent state is not being passed into the next call, see slide 10
