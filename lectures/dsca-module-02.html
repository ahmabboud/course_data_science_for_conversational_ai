Part one of two · about 25 minutes

An agent is a loop

First the plain version: one list of messages and one model call, repeated. Nothing is hidden.

Start with the word

An agent is a model that chooses the next step, in a loop

Definition

Agent: a program in which a model chooses the next step again and again (answer, use a tool, or hand over) until the task is done. Tool: a function in your code that the model may ask for.

The model asks, your code acts

The model never runs a tool. It asks for one.

Definition

Tool call: a message in which the model asks your code to run one tool, with chosen values. In Module 1 you met this as function calling. In today's demo the request is a small JSON object with an action field (call_tool, answer or escalate) and an order_id.

What you are actually calling, under any framework

One list, one call, one appended result. That is the whole loop.

messages = [
  {"role": "system", "content": "You are an order-status agent..."},
  {"role": "user",   "content": "can you check if order A100 shipped yet?"},
]
decision = call_model(messages)   # action: "call_tool", order_id: "A100"
messages.append({"role": "assistant", "content": "[call_tool]"})
result = get_order_status("A100")      # "shipped, arriving Thursday"
messages.append({"role": "tool", "content": result})
decision = call_model(messages)   # action: "answer"
messages.append({"role": "assistant",
                 "content": "Yes, order A100 has shipped..."})
# system, user, assistant [call_tool], tool, assistant [reply]
len(messages)   # 5
Definition

Message list: the list of everything said so far, each item tagged with a role (system, user, assistant or tool). The model keeps no memory, so this list is the memory, and your code sends all of it on every call.

The price of a model with no memory

Every call sends the whole list again

Invented for teaching: every message is 100 tokens, one message is added per turn.
Definition

Total after n turns = 100 × (1 + 2 + ... + n) = 100 × n × (n + 1) / 2. Twenty turns cost 21,000 tokens, not 2,000: the total grows with n times n.

Where just a list stops being enough

Three things the loop cannot tell you about itself

Question 1

What is true right now?

Has the user already told us an order number?

To know, you read the whole list and look for it.

Question 2

Can I stop and continue later?

The program stops. Can a new process continue from the same point?

Only if you saved the entire list yourself.

Question 3

Where is the decision?

Tool, answer or person: where does that choice live?

Usually in an if statement somewhere in your loop.

Structure and standards

The same agent with named parts, a standard for tools, a reason before every choice, and a way to hand over.

Same behaviour, now you can see the structure

The loop, drawn as nodes and edges

Definition

LangGraph: a Python library for writing an agent as a graph. Node: one step, a Python function that reads the state and returns changes. Edge: an arrow that says which node runs next. State: one named object that every node can read and update.

Check question

Compared with the raw loop, what does LangGraph add?

Two behaviours every dialogue agent needs

Ask when something is missing. Replace when the user corrects.

Definition

Clarification: the agent asks for a detail it is missing. Correction: the user changes an earlier detail, and the new value replaces the old one in the state. This sequence is invented for teaching: today's demo has no ask action.

Answer to question 2

A graph can save its state and resume

Without saving

The process ends. The state is gone. The next run starts empty.

With a checkpoint

After each node, LangGraph can save the state under a thread id. A new process loads it and continues from the same point.

Definition

Checkpoint: a saved copy of the state taken after a node runs. Thread id: the name of one conversation, used to find its checkpoints. Human-in-the-loop: the graph pauses before a node, shows a person the state, and continues only after they approve.

Honest note

Switching saving on is your choice (you give the graph a checkpointer). Today's demo does not, so each run starts from empty state. The reading before Module 3 covers it in full.

The part that is not LangGraph-specific

Write a tool once. Any agent can use it.

Definition

MCP (Model Context Protocol): an open standard for how an agent asks a tool server "which tools do you have?" and "run this one". An MCP server offers tools. An MCP client is the part inside an agent that talks to servers. A protocol is an agreed set of rules for messages.

How the agent node actually decides

Write the reason first, then choose the tool

Definition

Chain of thought: asking the model to write its reasoning before it commits to an answer. In today's demo the reason field comes last, so it explains the choice afterwards. That helps logs, but it is not reasoning first.

A trade-off, stated with its price

When is reasoning first worth the extra call?

Call the tool directly
  • Cheaper: one short generation, no reasoning text
  • Fine when only one tool could apply
  • Less reliable when similar tools differ only by a hint, such as status check or change
Reason first
  • A step that says what the request is asking for
  • Better choices among similar tools
  • Cost: a longer call every time, so use it where tools are easy to confuse
On purpose, only this one

One router, two places a turn can go

Definition

Router: the step that decides where a turn goes. Specialist path: nodes built for one job. Escalation: giving the turn to a person, together with the reason. In today's demo the agent node is the router, and its action field is the decision.

Watching the router make the boring, correct choice

The router decides. It never answers.

The reasoning behind 'only this one'

More agents means more places for a mistake to hide

What a team of agents adds
  • Each agent can have its own job and its own instructions
  • Some work can run in parallel
  • Useful when one agent's prompt would become too large
What it costs
  • More model calls: more money and more waiting
  • One agent can pass on another's mistake as a fact
  • Harder to see who decided what, and why
The rule of this course

Anthropic's guide Building Effective Agents (in the reading) advises finding the simplest solution possible and adding complexity only when it is needed. Our rule: start with one agent. Add a second only when you can name a job it does that the first cannot.

The ten criteria were: satisfaction, empathy, compliance, factuality, summary, acknowledgement, relevancy, language ease, frustration and smoothness. Experts rated Yes or No over three testing rounds. The conclusion states the objective range as 76% to 92%.
Definition

Agreement: how often the LLM judge (GPT-4.1) gave the same Yes or No as the experts. The paper's own conclusion: automatic judging is dependable for content, but not yet for emotional qualities, so people stay in the loop there.

A way to read the number

If both sides answered Yes or No at random, they would agree about half the time. So 60% is not far above chance. This is our reading, not the paper's.

Part 1 of the plain loop

A dictionary, and one function that calls the model

FAKE_ORDERS = {"A100": "shipped, arriving Thursday",
               "A200": "still processing, no ship date yet"}

def get_order_status(order_id):
    return FAKE_ORDERS.get(order_id,
        f"no order found for '{order_id}'")

def call_model(messages):
    transcript = "\n".join(
        f"{m['role']}: {m['content']}" for m in messages)
    reply = client.interactions.create(
        model="gemini-3.1-flash-lite", input=transcript,
        response_format={ ... "schema": DECISION_SCHEMA })
    return json.loads(reply.output_text)
What to notice
  • The tool is a plain dictionary lookup
  • call_model turns the whole list into one text and sends it
  • The reply must follow DECISION_SCHEMA: action, reply, order_id, reason (Module 1's idea)

The schema lists action first and reason last, which is why the reason here explains the choice afterwards.

Part 2 of the plain loop

Four steps and one if

def run(turn):
    messages = [system, user(turn)]        # step 1
    decision = call_model(messages)        # step 2
    messages.append(assistant(decision))

    if decision["action"] == "call_tool":
        result = get_order_status(          # step 3
            decision["order_id"])
        messages.append(tool(result))
        decision = call_model(messages)    # step 4
        messages.append(assistant(decision))

    return messages
What to notice
  • Four steps, the same four as the lecture slide
  • The list is the only state
  • The tool round runs once, with an if
A limit of this demo

A real agent uses a while loop that repeats while the model asks for tools, and stops after a maximum number of rounds so it cannot run forever.

Part 1 of the graph

The same call, wrapped as a node that reads and writes the state

class AgentState(MessagesState):
    order_id: Optional[str]
    route: Optional[str]
    reason: Optional[str]

def agent_node(state):
    decision = call_model(state["messages"])
    return {"messages": [AIMessage(...)],
            "order_id": decision.get("order_id")
                        or state.get("order_id"),
            "route": decision["action"],
            "reason": decision.get("reason")}
What to notice
  • call_model is the same call as in raw_loop.py
  • A node returns only the fields it changes
  • Messages are added to the list, not replaced
  • route is the model's action, saved by name

The tool and the model call are copied from the first file, not rewritten.

Part 2 of the graph

Two small nodes that never call the model

def tool_node(state):
    result = get_order_status(state["order_id"])
    return {"messages": [ToolMessage(result)]}

def escalate_node(state):
    return {"messages": [AIMessage(
        "Escalated to a human. Reason recorded: "
        + state["reason"])]}
What to notice
  • The tool node reads order_id from the state
  • The escalate node keeps the model's reason, so a person can read why
  • Neither node calls the model
Part 2 of the graph

Draw the map in a few lines

builder = StateGraph(AgentState)
builder.add_node("agent", agent_node)
builder.add_node("tool", tool_node)
builder.add_node("escalate", escalate_node)
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", route_from_agent,
    {"call_tool": "tool", "answer": END,
     "escalate": "escalate"})
builder.add_edge("tool", "agent")
builder.add_edge("escalate", END)
graph = builder.compile()
What to notice
  • Three add_node lines: one per node
  • Two plain edges and one conditional edge
  • tool → agent is the loop
  • compile checks the graph and makes it runnable

One habit to carry into your project

A decision without a reason is not documented

A good decision note

Routing decision. Legal questions go to human escalation, because a booking agent that answers them with confidence is worse than a short delay. No other routing was added.

A weak decision note

"We added routing."

It says what exists, not why. A reviewer cannot judge a decision they cannot read.

So you recognise them instead of debugging blind

Four problems you will meet

SymptomUsual cause
State resets every turnThe graph is started with empty fields each time instead of continuing the same conversation
The router always takes the same branchThe agent node never writes route, or the branch function reads a different field
The tool node loops for everThe model keeps choosing call_tool. Cap the number of rounds
A rate-limit or "model not found" errorCheck GOOGLE_API_KEY and GENERATION_MODEL in demos/.env; a free key has a daily request limit
Fastest way to tell which one you have

Print the state at the top of every node. If it does not change between turns, it is the first bug. If it changes and the router ignores it, it is the second.

Discussion

One clean routing case beats three guesses

Worth it when
  • A wrong answer costs a lot (money, safety, trust)
  • A person can do the job better
  • You can name the boundary in one sentence
Over-engineering when
  • Many routes that nobody ever triggers
  • The router starts answering instead of routing
  • A second agent has no job the first cannot do
