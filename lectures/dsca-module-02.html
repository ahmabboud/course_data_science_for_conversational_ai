Part one of two · about 25 minutes

An agent is a loop

First the plain version: one list of messages and one model call, repeated. Nothing is hidden.

Start with the word

An agent is a model that chooses the next step, in a loop

Definition

Agent: a program in which a model chooses the next step again and again (use a tool, or answer) until the task is done. Tool: a function in your code that the model may ask for.

The model asks, your code acts

The model never runs a tool. It asks for one.

Definition

Tool call: the model's request to run one tool, with chosen values. The model only writes the request. Your code runs it. You met this idea as function calling in Module 1.

What you are actually calling, under any framework

One list, one call, one appended result. That is the whole loop.

Definition

Message list: everything said so far, each item tagged with a role (system, user, assistant or tool). The model keeps no memory, so this list is the memory, and your code sends all of it on every call.

The price of a model with no memory

Definition

Token: a small piece of text the model reads (about three quarters of a word). Invented for teaching: every message is 100 tokens and one message is added per turn. Twenty turns cost 21,000 tokens in total, not 2,000.

Where just a list stops being enough

Three problems with just a list

Problem 1

What is true right now?

Has the user already given an order number?

Example: 5 messages in the list. To find out, you read all 5.

Problem 2

Can I stop and continue?

The program stops. Can a new process continue?

Example: it crashes after message 4. The list lived in memory, so it is gone.

Problem 3

Where is the decision?

Tool, answer or person: where is that choice made?

Example: a hidden if somewhere inside your loop.

What the next part builds

Next: give each thing a name. A field holds what is true now. A checkpoint is a saved copy. A labelled branch shows where the decision is made.

Invented for teaching · two behaviours every dialogue agent needs

Definition

Clarification: the agent asks for a detail it is missing. Correction: the user changes an earlier detail, and the new value replaces the old one in the state. Each row: what the user says, the state, what the agent does.

Answer to problem 2

A saved checkpoint lets a new process continue

Definition

Checkpoint: a saved copy of the state, taken after a node runs. Thread id: the name of one conversation, used to find its checkpoints.

Honest note

Switching saving on is your choice (you give the graph a checkpointer). Today's demo does not, so each run starts empty. A related feature, pausing for a person to approve a step, is in the reading AI Agents in LangGraph (last slide).

The part that is not LangGraph-specific

Write a tool once. Any agent can use it.

Definition

MCP (Model Context Protocol): an agreed set of rules (a protocol) for how an agent asks a tool server "which tools do you have?" and "run this one". The client is the agent's part that talks to servers.

Discover first, then call

The agent asks the server what it can do

Honest note

The two code snippets in the step captions are pseudo-code, written to show the idea. A server here means a program offering tools, not a website. Today's demo makes the same lookup with a normal Python function call.

How the agent node actually decides

Write the reason first, then choose the tool

Definition

Chain of thought: asking the model to write its reasoning before it commits. Schema: the fixed list of fields the model must fill in. Today's demo puts reason last, so it explains the choice afterwards: good for logs, but not reasoning first.

A trade-off, stated with its price

When is reasoning first worth the extra text?

Call the tool directly
  • Cheaper: a short output, no reasoning text
  • Fine when only one tool could apply
  • Less reliable when tools look alike
Reason first
  • The model first says what the request asks for
  • Better choices among similar tools. Example: "what about my order?" could mean get_order_status or cancel_order
  • Cost: more text on every call. Use it where tools are easy to confuse
The one place we split the work on purpose

A router only decides where the turn goes

Definition

Router: the step that decides where a turn goes. Order-status path: the nodes built for one job. Hand over (escalation): giving the turn to a person, together with the reason. In today's demo the agent node is the router.

The router makes the boring, correct choice

A billing question skips the tool and goes to a person

The reasoning behind 'only this one'

More agents means more places for a mistake to hide

What a team of agents adds
  • Each agent can have its own job and its own instructions
  • Some work can run in parallel
  • Useful when one agent's instructions would grow too long
What it costs
  • More model calls: more money and more waiting
  • One agent can pass on another's mistake as a fact
  • Harder to see who decided what, and why
The rule of this course

Anthropic's guide Building Effective Agents (linked on the last slide) says: find the simplest solution, add complexity only when needed. Our rule: start with one agent. Add a second only for a job the first cannot do.

Share of Yes or No ratings where the judge (GPT-4.1) agreed with the experts. The results say 79% to 92%; the conclusion says 76% to 92%, with no reason given. Ten criteria, three rounds.

Definition

Agreement: how often the judge gave the same Yes or No as the experts. The paper's conclusion: automatic judging is dependable for content, but not yet for emotional qualities, so people stay in the loop there.

A way to read the number

Two raters answering Yes or No at random would agree about half the time (if each answer is equally likely). So 60% is not far above chance. This is our reading, not the paper's.

Results, part 2

The safety parts were measured separately

Handoff agent

Precision and recall each above 90% across the key handoff cases.

  • Precision: of the handoffs it triggered, how many were right. 10 triggered, 9 right = 90%
  • Recall: of the cases that needed a handoff, how many it caught. 10 needed, 9 caught = 90%

The counts are an example, not the paper's.

Guardrails

Part 1 of the plain loop

The tool is a lookup. The model call sends the whole list.

FAKE_ORDERS = {"A100": "shipped, arriving Thursday",
               "A200": "still processing, no ship date yet"}

def get_order_status(order_id):  # 1 the tool
    return FAKE_ORDERS.get(order_id,
        f"no order found for '{order_id}'")
def call_model(messages):
    transcript = "\n".join(  # 2 list -> one text
        f"{m['role']}: {m['content']}" for m in messages)
    reply = client.interactions.create(
        model="gemini-3.1-flash-lite", input=transcript,
        response_format={ ... "schema": DECISION_SCHEMA })  # 3
    return json.loads(reply.output_text)
  • 1 The tool is a plain dictionary lookup
  • 2 call_model sends the whole list as one text
  • 3 The reply must follow the schema (Module 1)
DECISION_SCHEMA: four fields
action: call_tool, answer, escalate
reply: text for the user
order_id: the order, or empty
reason: why (listed last)
Part 2 of the plain loop

The demo loop: four steps, one tool round

def run(turn):
    messages = [system, user(turn)]        # step 1
    decision = call_model(messages)        # step 2
    messages.append(assistant(decision))

    if decision["action"] == "call_tool":
        result = get_order_status(          # step 3
            decision["order_id"])
        messages.append(tool(result))
        decision = call_model(messages)    # step 4
        messages.append(assistant(decision))

    return messages
What to notice
  • The same four steps as the list slide in Part 1
  • The list is the only state
  • The tool round runs once, with an if
A limit of this demo

A real agent uses a while loop that repeats while the model asks for tools, and stops after a maximum number of rounds so it cannot run forever.

Part 1 of the graph

A node reads the state and returns only what changed

def agent_node(state):
    decision = call_model(state["messages"])
    return {
      "messages": [AIMessage(...)],  # add the reply
      "order_id": decision.get("order_id")
                  or state.get("order_id"),  # keep old id
      "route": decision["action"],   # save the choice
      "reason": decision.get("reason")}  # save why
What to notice
  • call_model is the same call as in raw_loop.py
  • A node returns only the fields it changes
  • a or b means: use a, and if it is empty use b. So when the user gives no new order id, the old one stays (this is the correction slide)
  • AIMessage is a message written by the model

The state class is the one from the State slide.

Part 2 of the graph

Two small nodes that never call the model

def tool_node(state):
    result = get_order_status(state["order_id"])
    return {"messages": [ToolMessage(result)]}

def escalate_node(state):
    return {"messages": [AIMessage(
        "Escalated to a human. Reason recorded: "
        + state["reason"])]}
What the person sees

Escalated to a human. Reason recorded: a billing dispute is outside order status.

What to notice
  • The tool node reads order_id from the state
  • ToolMessage is a message holding a tool's result
  • The escalate node keeps the model's reason, so a person can read why
  • Neither node calls the model
Part 2 of the graph

Building the graph: nodes, edges, compile

builder = StateGraph(AgentState)
builder.add_node("agent", agent_node)
builder.add_node("tool", tool_node)
builder.add_node("escalate", escalate_node)
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", route_from_agent,
    {"call_tool": "tool", "answer": END,
     "escalate": "escalate"})
builder.add_edge("tool", "agent")
builder.add_edge("escalate", END)
graph = builder.compile()
What to notice
  • Three add_node lines: one per node
  • START and END are built-in markers for where the turn begins and ends
  • Two plain edges and one conditional edge (the table from the branch slide)
  • tool → agent is the loop
  • compile checks that every edge points at a real node, and makes the graph runnable

One habit to carry into your project · continuing the booking agent example

A decision without a reason is not documented

Keep: a good decision note

Routing decision. Legal questions go to human escalation, because a booking agent that answers them with confidence is worse than a short delay. No other routing was added.

Avoid: a weak decision note

"We added routing."

It says what exists, not why. A reviewer cannot judge a decision they cannot read.

So you recognise them instead of debugging blind

Four bugs and their usual cause

SymptomUsual cause
1 State resets every turnThe graph is started with empty fields each time instead of continuing the same conversation
2 The router always takes the same branchThe agent node never writes route, or the branch function reads a different field
3 The tool node loops for everThe model keeps choosing call_tool. Cap the number of rounds
4 A rate-limit or "model not found" errorCheck the API key and model name in the demo's settings file (demos/.env). A free key allows only so many requests a day: that limit is the rate limit
Fastest way to tell them apart

For bugs 1 and 2: print the state at the top of every node. If it does not change between turns, it is bug 1. If it changes and the router ignores it, it is bug 2.

Discussion

When is a routing rule worth adding?

Worth it when
  • A wrong answer costs a lot (money, safety, trust)
  • A person can do the job better
  • You can name the boundary in one sentence
More complex than needed when
  • Many routes that nobody ever triggers
  • The router starts answering instead of routing
  • A second agent has no job the first cannot do
