Part one of three · 50 minutes

From a raw loop to a managed graph

The same behavior, twice: once with nothing hidden, once with a framework that makes state explicit.

What you are actually calling, underneath any framework

One array, one call, one appended result. That is the whole loop.

Then the loop just repeats: append the result, call the model again with the whole array, see what it does next. There is no separate "state," the array is the state.

Where "just an array" stops being enough

Three questions the raw loop cannot answer about itself

  • Which fields are actually filled in right now, without re-reading the whole message history yourself?
  • Can you pause here and resume later, from exactly this point, in a different process?
  • If two things could happen next, depending on what the user just said, where does that branch live?
What today builds

The same three answers, but as an explicit, inspectable state object and a graph with real branches, not a convention you have to remember to follow.

The same loop, given structure

A graph with an explicit state object, instead of one growing array

END

The state object can be printed or logged at any point, mid-conversation, by a person, not just replayed as a wall of messages. That is the actual, concrete thing "explicit state" buys you.

Check question

What does LangGraph actually add that the raw loop, run correctly, did not already have?

The idea behind the question

Frameworks earn their keep by making an existing idea inspectable and reusable, not by inventing a new idea.

The part that is not LangGraph-specific

One protocol for "what tools exist and how do I call them"

Without a standard

Every tool integration is its own bespoke function signature and error shape, wired by hand, and adding a new tool source means writing new glue code again.

No. MCP is a protocol, independent of any one framework. LangGraph nodes can call tools wired through MCP, but the standard itself exists so an agent built on a different framework entirely could call the exact same tool server.

What "discover, then call" looks like turn by turn

The agent node never hardcodes what a tool takes

tools = mcp_client.list_tools()
# names, argument shapes, all supplied by the server
reply.tool_call: "get_order_status", {order_id: "A100"}
result = mcp_client.call("get_order_status", order_id="A100")
result: {order_id: "A100", status: "shipped"}
# or, on failure: a typed error, not a raw traceback

Watching the model reason its way to the right tool

Do this part by hand first

Four calls, the whole mechanism, before any framework

messages = [
  {"role": "system", "content": "You can call get_order_status."}
]
messages.append({"role": "user", "content": turn})
reply = call_model(messages, tools=[get_order_status])
result = get_order_status(**reply.tool_call.args)
messages.append({"role": "tool", "content": result})
reply = call_model(messages, tools=[get_order_status])
# repeat from step 3 if reply is another tool call
Rebuild, do not rewrite from scratch

Same call, same tool, now as an explicit graph

class AgentState(TypedDict):
    messages: list
    order_id: str | None
def agent_node(state: AgentState):
    reply = call_model(state["messages"], tools=[get_order_status])
    return {"messages": state["messages"] + [reply]}
graph.add_conditional_edges(
  "agent", needs_tool, {True: "tool", False: END}
)
print(state["order_id"])  # readable, not reconstructed
Not a hand-rolled function call

Discover the tool, do not hardcode its shape

def tool_node(state: AgentState):
    tool = mcp_client.get_tool("get_order_status")
    # the client, not your code, knows the call shape
    result = tool.call(order_id=state["order_id"])
    return {"messages": state["messages"] + [result]}
Likely blocker

A tool call that raises instead of returning cleanly. Catch it in the tool node and append a tool-role error message, the same way a failed extraction call gets a fallback in Module 1, do not let it crash the graph.

Pause here before you touch routing

Three things to check before moving on

CheckHow to confirm it
The tool node calls through the MCP client, not a hardcoded functionGrep your tool node for a direct import of the lookup function, it should call mcp_client instead
A failed tool call does not crash the graphPass an invalid order id on purpose and confirm the graph still reaches END with a message, not a traceback
State actually threads across turnsPrint state["order_id"] at the top of the agent node on a second turn, it should already be set
Why pause here

Routing built on top of a shaky tool node just hides the real bug under a new one. Confirm this part is solid first, it is faster than debugging both at once later.

One case, chosen deliberately

Pick the one boundary your agent should never cross alone

Every domain has at least one request type that should not be handled by the same path as everything else: something outside scope, something irreversible, something that needs a person's judgment. That is your routing or escalation case for Issue 2, exactly one, not a general router for everything.

Not required

A second specialist path, or a general-purpose router. One clean branch, done well, is the acceptance criterion, not a bigger graph.

Decide out loud, with your partner, before you code

A user asks something clearly outside your agent's domain (say, a legal question to a booking agent). Which routing choice fits best?

Write it down where the reviewer will look

One paragraph in the PR description, not a design doc

## Routing decision
Legal questions route to human escalation because a
booking agent answering them confidently is worse than
a short delay. No other routing was added.
Trap

"We added routing" with no reasoning is not a documented decision. Acceptance criteria ask for the reasoning, not just the branch existing.

So you recognize them instead of debugging blind

Four bugs that show up in almost every team's graph today

SymptomUsual cause
State resets every turnThe graph is invoked fresh each call instead of threading the same state object through
Router always picks the same branchThe condition function reads a field the agent node never actually sets
Tool node loops foreverThe conditional edge back to the agent node has no exit condition once the tool succeeds
MCP call raises and crashes the graphNo try/except in the tool node, see the previous slide's callout

Print the state object at the top of every node. If it does not change between turns, it is the first bug. If it changes but the router ignores it, it is the second. Do this before reading any stack trace.

Only once your one required case is merged-ready

Finished early? Add a second boundary, do not widen the first one

Issue 2 only requires one routing or escalation case. If your team's is done, tested, and documented, a second, genuinely different case is a good use of remaining time: a different kind of out-of-scope request, or a second high-stakes action that should stop for a person. Do not spend this time widening the first case's conditions instead, that is the over-engineering trap the discussion at the end of today names directly.

Not a requirement

A team with one clean, well-tested case and time left over should keep testing it, not necessarily add a second. This slide is for teams asking "what next," not a new minimum bar.

Open work · rest of the block

Raw loop, then LangGraph, then routing. In that order.

  3. Add your one routing or escalation case and its PR paragraph.

Discussion · 14 minutes

When routing earns its complexity, and when it is over-engineering

  • One clean routing case, well-tested, beats three speculative ones nobody has actually triggered yet.
  • Module 3 gives every specialist path a real retrieval-grounded answer, so today's routing is what decides which questions even reach it.
  • Report any blocker from today in your team's channel before Module 3, not at the start of it.
Ask the room

If a team built the stretch slide's second routing case today, ask them to name the actual boundary out loud, it is a good live check for whether "genuinely different case" landed or whether it just widened the first one.
