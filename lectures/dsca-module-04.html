Part one of two · 50 minutes

Memory that survives the session

Two ways to persist a fact, a third way to keep a conversation from overflowing, and what it all costs in privacy risk.

What Module 3's agent still cannot do

Every new session, the agent meets the user for the first time

Session 1, turn 1
Session 1 ends

Session memory (the message list) is not the gap. Persistent, cross-session memory is: nothing written today is available to a session that has not even started yet.

Today's two working examples

Two different answers to "where does a fact live once the session ends"

Extract, then update a flat list

Pull facts out of each turn, compare each one to what is already stored, and issue one instruction: add it, fix an existing fact, drop a contradicted one, or do nothing. Mem0 is today's worked example.

Build a graph that carries time

Represent facts as edges between entities, each edge stamped with when it became true and when, if ever, it stopped being true. Zep, via its graph engine Graphiti, is today's worked example.

Both reject the same naive option: just re-feeding the entire conversation history back to the model every session, which is exactly what Module 3's cache-augmented generation question already showed does not scale past a small, stable knowledge base.

Mem0: a flat memory bank, kept clean

Every new fact gets compared to what you already know

turn: "I just moved from Beirut to Paris for work."
# extracted candidate: {"text": "lives in Paris", "entity": "user"}
existing: "lives in Beirut"   similarity(new, existing) = 0.86
# high similarity: this is very likely an update to the same fact,
# not a new, unrelated one
ADD     # genuinely new fact, no close existing match
UPDATE  # contradicts or refines an existing fact ("Beirut" -> "Paris")
DELETE # existing fact is now explicitly false
NOOP   # candidate already fully covered by what is stored
UPDATE("lives in Beirut" -> "lives in Paris")
# one current fact, not two contradictory ones sitting side by side

Step 2 is a similarity search against the entire existing memory bank for every single incoming fact. Done naively, that is O(n) comparisons per new fact against n stored facts, the exact same scaling concern Module 3 raised about vector search at scale: a small personal memory bank never notices, a memory bank shared across many users or growing for months needs the same approximate-nearest-neighbour indexing already covered for document retrieval, not a linear scan re-derived from scratch.

On real benchmarks (LOCOMO, GPT-4o-mini scale), Mem0 answers from roughly 1,764 tokens of retrieved memory versus 26,031 tokens for replaying the full transcript, about 15 times less context per query, at a median search latency of about 0.15 seconds.

Zep / Graphiti: facts that carry a timeline

A fact is never deleted, it is closed and superseded

Raw episodes (messages)
Communities
The same "lives in Paris" example, as a graph

edge(user, lives_in, Beirut), valid_at: 2025-01, invalid_at: 2025-09. edge(user, lives_in, Paris), valid_at: 2025-09, invalid_at: null. Both edges stay in the graph; a query about last January still gets the right answer, a query about today gets the other one.

Check question

A user asks, "where did I live before I moved to Paris?" Which memory pattern can answer this, and why?

The idea behind the question

A flat extract-and-update store optimises for "what is true right now, as compactly as possible." A temporal graph optimises for "what was true when," at the cost of a richer, more expensive structure to build and query.

The other half of memory: not overflowing in the first place

A conversation that never ends still has to fit in a context window

  • Truncation. Drop the oldest turns once a budget is hit. Cheapest option, and the one most likely to silently drop the exact fact a later question needs.
  • Summarisation. Periodically compress old turns into a running summary. Keeps more, but a summary quietly loses the details Module 3's chunking slide already warned about.
  • Segment, then compress. Split the conversation into topically coherent segments first, then denoise each segment with a prompt-compression model before it ever reaches retrieval. SeCom is this course's third technique, assigned as this module's reading rather than a full research dive.
SeCom's own reported numbers

On LOCOMO, reading back the full transcript scores 54.2 (GPT4Score); segment-then-compress scores 71.6, a +17.4 point gain, using a compression rate of about 75% (LLMLingua-2). Removing the compression step alone costs 9.46 of those points back, the paper's own ablation, not a rounded estimate.

The bill that comes with remembering

A memory bank is a record, and records have obligations

  • Every persisted fact is, by construction, data retained about a specific person, often including things they mentioned in passing and never meant to be stored indefinitely.
  • A memory bank keyed by the wrong identifier can leak one user's facts into another user's session, a bug that looks like "the agent is confused" until it is traced back to a shared or mis-scoped store.
  • A stored fact that is wrong, outdated, or sensitive does not fix itself, and a user has no way to know what the agent "remembers" about them unless the system is built to say so.

Read critically, not as a leaderboard

SeCom's own numbers are strong on LOCOMO, but SeCom was built to answer "how should I chunk and denoise one long conversation," not "how do I track a fact that changes over months across many sessions," the problem Mem0 and Zep are actually built for. A benchmark win on one axis does not make a technique the right choice on a different axis.

Extract and update, or track over time, then compact so nothing overflows

Build it: memory across two sessions

Hands-on lab · 100 minutes · starts now

Give your Module 3 agent persistent, cross-session memory

  1. Wire Mem0 in: extract facts from each turn, add them to a per-user memory bank.
  2. Retrieve relevant memories for the current query, and feed them into your existing grounded-generation pipeline from Module 3.
  3. Prove it: recall a specific user's stated fact in a second, genuinely separate session.
  4. Add compaction so a long conversation is summarised, not silently truncated or overflowed.
Deliverable · Issue 4

Merged: the agent demonstrably remembers a specific user across two separate sessions, with a working compaction strategy for long conversations.

One call per turn, four possible outcomes

Add a memory call after every turn, keyed by user, not by session

pip install mem0ai
from mem0 import Memory
memory = Memory()
memory.add(messages, user_id="user-482")
# user_id identifies the person, across every session they ever start
result = memory.add(messages, user_id="user-482")
print(result["results"])
# [{"memory": "lives in Paris", "event": "UPDATE"}]
# stop the process entirely, start a new one:
memory.get_all(user_id="user-482")
# the facts are still there, because they never lived in the process
Memory is just one more source, not a new pipeline

Search memory, merge it with document retrieval, cite it the same way

relevant = memory.search(query, user_id="user-482", limit=5)
memory_chunks = [{"source_id": f"memory#{m['id']}", "text": m["memory"]} for m in relevant]
candidates = memory_chunks + document_chunks
# same rerank(), same coverage_check(), same answer_with_citation()
{"answer": "You mentioned you live in Paris.", "cited_sources": ["memory#f-118"]}
Pause here before compaction

The rubric bar, tested literally, not assumed

CheckHow to confirm it
Facts are keyed by user, not sessionGrep your own code for every memory.add and memory.search call, confirm user_id, not session_id or conversation_id
Recall survives a real process restartKill the script, start a new process, ask the agent something only revealed in the earlier run
Deduplication actually firesState the same fact two different ways in two turns, confirm the second produced UPDATE or NOOP, not a second ADD
Why pause here

This is the literal deliverable for Issue 4. A team that has only tested recall inside one long conversation has not actually tested the thing being graded, catching that now is far cheaper than at the checkpoint discussion.

The other half of Issue 4

Summarise the old, keep the new, never silently drop or overflow

MAX_LIVE_TURNS = 20
# once exceeded, the oldest turns are summarised, never just dropped
old_turns = messages[:10]
summary = summarize(old_turns)
messages = [summary] + messages[10:]
# rolling summary: keeps THIS session coherent as it gets long
# Mem0 memory bank: keeps facts alive ACROSS sessions
# both are needed; neither substitutes for the other

So you recognize them instead of debugging blind

Four bugs that show up in almost every team's memory today

SymptomUsual cause
Recall "works" but only inside one runMemory keyed by session_id, or backed by an in-process store that never actually persists to disk
The same fact appears twice, sometimes contradicting itselfmemory.add called without checking the result, so a silent duplicate ADD was never caught
One user sees facts about a different useruser_id hardcoded, or derived from something shared across users, such as a fixed test string
A long conversation eventually errors on context lengthThe rolling-summary budget check was written but never actually wired into the main loop

Print user_id and the full memory.add result on every call, before doing anything else. If a second run cannot see the first run's facts, it is the first bug. If the same claim appears twice under different ids, it is the second. If two different test user_ids ever return the same memories, it is the third.

Only once recall and compaction both work

Implement the operation the privacy slide promised

A single call that deletes every stored memory for one user_id, wired to an actual phrase a user could plausibly say ("forget everything about me"). Confirm afterward that memory.get_all for that user_id returns nothing, and that the agent genuinely no longer recalls the deleted facts, not just that the call ran without an error.

Not a requirement

Issue 4 only requires working recall and compaction. This is for teams whose basic path already works and want to make today's privacy discussion concrete in their own system.

Discussion · 14 minutes

Three failure modes, each with a real cost

Stale facts

A fact was true, then changed, and the agent never found out, so it confidently states something that stopped being true.

Wrong recall

A fact gets attached to the wrong user, or the wrong entity, and the agent confidently tells someone something true about somebody else.

Discuss

For each failure mode: how would your team's own memory design actually catch it, and what would a user experience before anyone noticed?

Then, briefly: what should happen, concretely, when a user asks the agent to forget something?
