Part one of four · 35 minutes

Retrieval you can actually trust

Hybrid search, reranking, chunking, and the discipline of knowing when not to answer.

The default architecture, not an advanced option

Two very different ways to find the right passage, run together

Keyword search alone misses a paraphrase. Vector search alone misses an exact identifier. Run both, every time, and let fusion decide what actually floats to the top.

score(term, doc) = IDF(term) * ( tf * (k1+1) ) / ( tf + k1 * (1 - b + b * doclen/avgdoclen) )
# tf saturates: a term's 10th occurrence adds far less than its 2nd did
# k1 (about 1.2 to 2.0) sets how fast it saturates; b (about 0.75) penalises long documents
similarity(q, d) = ( embed(q) . embed(d) ) / ( ||embed(q)|| * ||embed(d)|| )
# embed() is a bi-encoder: query and document are each encoded separately,
# never seeing each other, which is exactly what lets every document's
# vector be precomputed once, offline, before any query arrives

Neither index actually scans every document at query time once a corpus is large. A real vector index is an approximate nearest-neighbour (ANN) structure, commonly HNSW (a navigable graph built over the embedding space) or IVF (cluster the embeddings once, search only the nearest clusters at query time). Both trade a small, tunable amount of recall for query time closer to logarithmic in corpus size than the O(n) linear scan an exact search would need.

Merging two rankings without retuning anything

Reciprocal rank fusion: one ranked list from two

BM25 rank:    [p7, p2, p9, ...]
Vector rank:  [p2, p5, p7, ...]
score(p) = sum over each list:  1 / (k + rank_in_that_list)
# k is a small constant (commonly 60), not a tuned weight
score(p2) = 1/(k+2) + 1/(k+1)   # high in both
score(p7) = 1/(k+1) + 1/(k+3)   # high in BM25 only
final order: [p2, p7, p9, p5, ...]
# no "trust BM25 70%, vector 30%" knob to tune per domain
# CombSUM: score(p) = sum of each list's raw score for p
# CombMNZ: score(p) = CombSUM(p) * (number of lists p appears in)
# both need scores on the same scale; BM25 and cosine similarity are not
Check question

What does combining hybrid search with reciprocal rank fusion actually buy you, that a single retrieval method alone does not?

The idea behind the question

Hybrid search is a robustness argument, not a raw-accuracy argument: it removes a whole class of query your pipeline would otherwise silently fail on.

Fast and broad, then slow and precise

A second pass that actually reads the query against each candidate

Top 5 to the LLM

Retrieval is cheap and wide on purpose. Reranking is expensive and narrow on purpose. Running the expensive step over the whole corpus, instead of a few dozen candidates, is the mistake this two-stage split exists to prevent.

Retrieval's bi-encoder embeds the query and every document separately, so each document's vector was already computed once, offline: query time is close to O(1) per document once an ANN index is in front of it. A cross-encoder reranker feeds the query and one candidate through the model together, jointly, so nothing about it can be precomputed ahead of the query: reranking n candidates costs O(n) full forward passes, paid entirely at query time. That is exactly why it only ever runs on the 20 to 50 candidates fusion already narrowed things to, running it over an entire corpus would multiply that O(n) cost by a corpus size in the thousands or millions.

The reranker itself is typically trained with a learning-to-rank objective (a pairwise or contrastive loss over known relevant/irrelevant pairs), not the same objective the embedding model was trained with, which is part of why its judgment differs from, rather than merely repeats, the fusion ranking that fed it.

The decision that happens before any of this runs

A badly chunked source material breaks every stage above it

chunk: "...arrives within 3 to 5 business days."
# days after WHAT? the preceding sentence is gone
# one chunk = an entire policy page, 40 unrelated paragraphs
# the one relevant sentence is buried in noise
chunk_size = 500, overlap = 50
# the last 50 tokens of chunk N reappear as the first 50 of chunk N+1
# split on headings/paragraphs first, THEN cap size within each
# not: split every 500 characters regardless of what that cuts
The last question before the agent speaks

Does the reranked context actually answer this, or not

Today's pipeline, in one line

Hybrid retrieve, rerank, then decide whether to answer at all

  • Hybrid search casts a wide, robust net across exact terms and paraphrases.
  • Reranking narrows that net to the few passages actually worth reading closely.
  • The coverage check decides, only then, whether to answer with a citation or refuse.
A question worth sitting with

This whole pipeline exists to compensate for one thing: a context window too small to hold the entire knowledge base at once. What if it wasn't too small?

Part two of four · 20 minutes

One paper says you might not need any of this

A single short paper, read closely: the idea, the challenge it answers, the experiment, and the result.

Cache-augmented generation (CAG)

Preload everything offline, so inference never has to retrieve at all

Query
Documents
Chan, Chen, Cheng & Huang, WWW '25

"Don't Do RAG: When Cache-Augmented Generation Is All You Need for Knowledge Tasks" (arXiv:2412.15605)

A visual summary of the same idea, for your own reference

RAG vs CAG, side by side

The problem this paper is answering

Three real costs of retrieval, and a trend that undercuts them

  • Retrieval latency. Every query pays for a search step before generation can even begin.
  • Retrieval errors. The wrong passage, or a missing one, silently changes what the model can possibly say.
  • System complexity. An index to build, a vector store to run, a reranker to serve: real infrastructure, for every deployment.
The enabling trend

Long-context LLMs now hold far more than a small knowledge base needs. Llama 3.1 was trained with a 128K-token context. If the whole source collection already fits, what is the retrieval step even for?

How the paper actually tested this

CAG against BM25 and dense RAG, on two QA benchmarks

SetupDetail
BenchmarksSQuAD 1.0, and HotPotQA (multi-hop questions)
ModelLlama 3.1 8B, run on 8× Tesla V100 32GB GPUs
RAG baselinesBuilt with the LlamaIndex framework: BM25 (sparse) and OpenAI embeddings (dense), each tried at top-1, top-3, top-5, and top-10
CAGThe full reference document set preloaded per dataset, KV cache precomputed once, no retrieval step at inference
MetricBERTScore: semantic similarity between the generated answer and the ground-truth answer
Why two benchmarks

SQuAD questions are answerable from one passage. HotPotQA questions need reasoning across multiple passages, a harder, more realistic test of whether preloading everything actually holds up.

A metric worth naming plainly

BERTScore checks whether the generated answer resembles a reference answer: an end-task metric. It says nothing directly about whether retrieval itself found the right passage. The field's standard metrics for that separate question are Recall@k (is a relevant passage anywhere in the top k), MRR (how high the first relevant result ranks, averaged over queries), and nDCG (relevance credited more, discounted the further down the ranking it sits). This paper reports none of them, worth noticing when reading its retrieval numbers.

What the paper itself says CAG cannot do, and one thing it does not say

A real limit, stated by the authors, and one they underplay

The paper's stated limitation

CAG "requires loading all relevant documents into the model's context," which the authors say fits "internal knowledge bases of small companies, FAQs, and call centers," but "becomes impractical for significantly larger datasets." They expect this to matter less as context windows keep growing.

A tension the paper's own framing underplays

"Retrieval latency at zero" describes the query, not the whole cost: the KV cache still has to be precomputed from the entire preloaded context, and that prefill compute, plus the cache's storage, scales with corpus size even though it happens offline. Separately, a longer context is not free at inference either: Liu et al.'s "Lost in the Middle" found models attend unevenly across a long context, favouring information near the start or end, and answer worse when the relevant fact sits in the middle. A bigger preloaded cache puts more of the answer in exactly that middle.

Applied question, for today's lab

Does the case for CAG over RAG hold for your team's own domain, and why or why not? Weigh the paper's own limitation and the tension above, not just the paper's headline claim. You will argue this directly at the end of today's session, against your own knowledge base.

Part three of four · 90 minutes

Build it: retrieve, rerank, cite, refuse

Once you understand the pipeline, and know when it might be more than your own domain needs.

Hands-on lab · 90 minutes · starts now

Ground your Module 2 agent in your team's own source material

  1. Build a hybrid-search retrieval layer (BM25 plus vector) over your own source material, merged by reciprocal rank fusion.
  2. Add a reranking pass that narrows the merged candidates to the few worth answering from.
  3. Wire retrieval into your Module 2 agent, with a citation attached to every grounded answer.
  4. Implement a refusal path for questions your source material does not actually cover.
Deliverable · Issue 3

Merged: the team's agent grounds its answers in a real source, cites them, and has a working refusal path for unsupported questions.

Both retrieval modes, then fuse

Index once, query twice, merge by rank

bm25_index = BM25Index.build(documents)
vector_index = VectorIndex.build(documents, embed_fn)
bm25_hits = bm25_index.search(query, top_k=20)
vector_hits = vector_index.search(query, top_k=20)
merged = reciprocal_rank_fusion([bm25_hits, vector_hits], k=60)
# merged[:30] moves on to the reranking pass, next walkthrough
Narrow before you answer

From thirty plausible candidates to five worth reading

candidates = merged[:30]   # from the fusion step, not the whole corpus
scores = [reranker.score(query, c) for c in candidates]
reranked = sort_by_score(candidates, scores)
final_context = reranked[:5]
Pause here before you wire in citation and refusal

Three things to check before moving on

CheckHow to confirm it
Both retrieval modes actually runLog the BM25-only and vector-only hit lists separately before fusion, confirm both are non-empty on a real query
Fusion changes the orderingCompare the merged top-5 against BM25-only top-5; if they are always identical, the vector results are not actually contributing
Reranking narrows meaningfullyConfirm the reranked top-5 is not simply the fused top-5 in the same order; if it always is, the reranker call is not wired in
Why pause here

Citation and refusal, next, both depend on the reranked context actually being the best available context. Debugging a bad answer once three stages are stacked is much harder than catching a weak retrieval layer now.

The coverage check, wired for real

Decide whether to answer before generating anything final

coverage = judge_coverage(query, final_context)
# returns: covered (bool), reason (str)
if coverage.covered:
    return answer_with_citation(query, final_context)
else:
    return refuse(query, coverage.reason)

So you recognize them instead of debugging blind

Four bugs that show up in almost every team's pipeline today

SymptomUsual cause
Vector search never changes the fused rankingEmbeddings computed with a mismatched model between indexing and query time, so similarity scores are meaningless
Citations point at the wrong passageSource ids attached at indexing time were dropped somewhere before the final prompt, so the model is citing from memory, not from the actual context
Refusal path never fires, even on clearly uncovered questionsThe coverage check prompt asks whether the context is "related," not whether it "answers," which almost anything passes
Chunk boundaries cut a fact the citation later points atChunking by fixed character count instead of structural boundary, see the lecture's chunking slide

Print the source id and raw chunk text alongside every answer, before rendering anything to the user. If the cited id's actual text does not support the claim, it is the second bug. If refusal never triggers on an obviously uncovered test question, it is the third.

Only once citation and refusal both work on the easy cases

Write the question designed to trick your own coverage check

A question that sounds answerable, uses the right vocabulary, mentions the right product or topic, but is not actually addressed anywhere in your source material. If your refusal path is well built, it catches this. If it is not, this is exactly where it fails first, and far better to find that now than to have a user find it later.

Not a requirement

Issue 3 only requires a working refusal path on the straightforward case. This adversarial test is for teams whose basic path already works and want to pressure-test it.

Open work · rest of the block

Hybrid search, then rerank, then citation and refusal. In that order.

  1. Finish wiring hybrid search plus reranking over your own source material.
  2. Wire the agent's answer to a citation, using the source ids carried through from indexing.
  3. Add the coverage check and refusal path, and test it against at least one genuinely uncovered question.
  4. Open the PR. Closes #3 in the description links it automatically.
A pipeline on paper is not the deliverable

Issue 3 needs a real answer, with a real citation, and a real refusal on a question you actually tried. If a live connection drops mid-session, keep testing against locally cached retrieval results, the citation and refusal logic does not need a live connection to verify.
